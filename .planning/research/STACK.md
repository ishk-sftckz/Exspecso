# Technology Stack

**Project:** Exspecso  
**Researched:** 2026-08-18  
**Recommendation confidence:** MEDIUM — primary vendor documentation and the npm registry were checked on the research date. Runtime extension surfaces move quickly; capability detection and adapter-contract tests remain required.

## Recommended Stack

Exspecso should be a **single, ESM-only Node.js CLI package**. Its core is a deterministic artifact engine; runtime integrations are install-time templates and thin prompts which call that engine. Do not embed an agent runtime SDK or create a service layer. This preserves one package, local-first operation, and Markdown/JSON artifacts as the sole project truth.

### Core Framework

| Technology | Version | Purpose | Why |
|---|---:|---|---|
| Node.js | `>=24` (test 24 and current) | Runtime, filesystem, subprocesses, crypto, JSON, and test execution | Node 24 is the minimum supported LTS line for the package. Node’s release policy says production applications should run Active or Maintenance LTS. A modern Node floor removes legacy CommonJS and polyfill compatibility work while retaining a broadly installed runtime. |
| TypeScript | `^7.0.2` | Strict implementation language and artifact/helper types | The project has complex state transitions and many small data contracts. `strict` TypeScript makes illegal state shapes difficult to represent while keeping CLI, helper, and adapters in one language. |
| Native Node APIs | Node 24 | Files, atomic writes, hashing, process execution, Git calls | Use `node:fs/promises`, `node:path`, `node:crypto`, `node:child_process`, and `node:readline/promises`. They cover V1 without extra operational dependencies. Run Git through `execFile`/`spawn` with argument arrays, never a shell string. |
| NodeNext ESM | TypeScript `module: "nodenext"`; package `type: "module"` | Module system | This is a Node CLI, not a bundled browser app. TypeScript explicitly recommends Node-aware module settings for Node projects; `bundler` resolution can permit imports that fail in Node. Emit one ESM executable. |
| Commander | `^15.0.0` | CLI command parsing, help, options, and subcommands | Stable, small, and sufficient for `init`, `status`, artifact inspection, and deterministic helper commands. Keep interaction in the CLI layer; domain functions accept typed input and return typed results. |
| Zod | `^4.4.3` | Validation at file and adapter boundaries | Validate every JSON document, frontmatter object, adapter input, and persisted state before it enters the state engine. Zod 4 is stable and gives useful user-facing diagnostics without inventing a second persistence model. |
| YAML | `^2.9.0` | Parse and serialize limited Markdown YAML frontmatter | Use only for explicit frontmatter in canonical Markdown. Markdown body text remains human-authored and opaque to the schema engine. Emit a small documented subset; do not turn artifacts into a YAML application. |

### Database

| Technology | Version | Purpose | Why |
|---|---:|---|---|
| Repository Markdown + small JSON | N/A | Canonical project model and evidence | This is deliberately the database substitute. Files are directly readable, diffable, mergeable, portable across all three runtimes, and available offline. |
| Git | User-installed Git 2.x+ | Verified-task checkpoint and history | Git is the durable checkpoint mechanism required by the product. The helper derives and verifies the expected commit boundary; it never stores authoritative state in Git notes, a cache, or a database. |

**Do not add SQLite, an ORM, a hidden cache, or a hosted store in V1.** They would create a second source of truth and compromise cross-runtime resumption.

### Infrastructure

| Technology | Version | Purpose | Why |
|---|---:|---|---|
| npm registry distribution | npm package | Installation via `npx exspecso init` | `package.json#bin` is the native npm mechanism for placing the `exspecso` executable on the PATH. Ship exactly one published package and one codebase. |
| Package contents allowlist | `package.json#files` | Publish only executable code and adapter assets | Publish `dist/`, `runtime-templates/`, `README.md`, `LICENSE`, and required metadata. This avoids accidentally shipping tests, design scratch files, or development configuration. |
| GitHub Actions (or equivalent CI) | Node 24 + current Node matrix | Typecheck, test, packed-artifact smoke test, and release gate | CI is release validation only; it is not a control plane. Test the tarball generated by `npm pack`, because `npx` users exercise published contents rather than the working tree. |
| No daemon / no network service | N/A | Local-first execution | Commands are explicit processes. They read repository artifacts, perform one bounded operation, write atomically, and exit. No background worker, telemetry requirement, credentials, or cloud control plane is needed for V1. |

### Supporting Libraries

| Library | Version | Purpose | When to Use |
|---|---:|---|---|
| tsup | `^8.5.1` | Build the single ESM CLI into `dist/` | Bundle the CLI entrypoint only. Copy non-code runtime templates as package assets in an explicit post-build step. Exspecso is a CLI, not a public general-purpose library, so a compact executable matters more than dual-module consumption. |
| Vitest | `^4.1.10` | Fast unit and integration tests | Test schema parsing, state derivation, allowed transitions, idempotent installs, recovery terminal results, and file fixtures. Use isolated temp repositories for CLI subprocess tests. |
| fast-check | `^4.9.0` | Property-based tests for the deterministic state engine | Use for transition matrices, recovery-attempt limits, idempotence, and “derived state never marks incomplete work verified” invariants. This is unusually valuable because Exspecso’s core risk is incorrect control logic, not HTTP behavior. |
| tsx | `^4.23.12` | Run local TypeScript maintenance scripts | Use only in development scripts, never as the installed CLI runtime. Published users execute compiled Node ESM. |
| ESLint | `^10.8.1` | Static linting | Apply to implementation and tests with project-local rules. Do not use lint output as completion evidence for product tasks; it is one declared evidence type. |
| Prettier | `^3.9.6` | Formatting | Format source, JSON, and adapter templates. Do not automatically reformat user-owned canonical artifacts during routine workflow operations. |
| publint | `^0.3.23` | Published-package metadata validation | Run before release to catch broken `bin`, `files`, exports, and package metadata. |

## Package and Repository Shape

Keep the repository as one package, with code boundaries rather than workspace/package boundaries:

```text
src/
  cli/                 # Commander commands and user-facing diagnostics
  domain/              # Zod schemas, transition guards, derivations; no I/O
  artifacts/           # Markdown/JSON read, validate, atomic write, references
  git/                 # narrow Git command wrapper and checkpoint checks
  adapters/            # runtime capability probes and template rendering only
  install/             # idempotent, interruption-safe installation coordinator
runtime-templates/
  claude-code/         # plugin/skill or project command assets
  codex/               # AGENTS.md/skill/config-facing wrapper assets
  opencode/            # .opencode command assets
tests/
  fixtures/            # tiny repositories and expected artifact states
```

The package contract should be deliberately narrow:

```json
{
  "type": "module",
  "bin": { "exspecso": "./dist/cli.js" },
  "engines": { "node": ">=24" },
  "files": ["dist", "runtime-templates", "README.md", "LICENSE"]
}
```

Generate `dist/cli.js` with a Node shebang. The CLI owns argument parsing and terminal output; the domain layer must be callable without Commander, a terminal, Git, or a particular agent runtime. Every mutation follows: read → validate → derive/check preconditions → write temp file in the target directory → rename → re-read/validate when the command claims success.

## Native Runtime Integration Choices

| Runtime | V1 integration surface | Recommendation |
|---|---|---|
| Claude Code | Plugin/skill/command assets; project-local configuration where appropriate | Package a native Claude-facing bundle and let `init` install only when selected. Claude plugins support skills, hooks, agents, MCP, and `bin/`; use only commands/skills plus the packaged deterministic helper in V1. Do not make an MCP server or lifecycle hook necessary for core semantics. |
| OpenAI Codex | `AGENTS.md` for durable repo guidance, `.agents` skills for reusable workflow content, and minimal project `.codex` assets only when necessary | Generate thin wrappers that invoke/read Exspecso artifacts and CLI results. Keep the canonical policy outside AGENTS.md so it is not duplicated or dependent on a single runtime’s prompt-loading behavior. |
| OpenCode | `.opencode/commands/*.md` and project configuration | Prefer documented Markdown commands because they are a stable, file-native surface. **Do not make OpenCode V2 plugins a V1 dependency:** its official documentation marks V2 plugin API entrypoints/hooks/configuration as beta. |

Adapters are renderers and capability probes, never alternate workflow engines. They may translate a canonical operation into native invocation syntax, but must not calculate status, create a divergent state file, or change the evidence contract. Feature-detect the installed runtime and write only selected assets; report an actionable compatibility error instead of guessing.

## Tooling and Verification Baseline

Use the following scripts from day one:

```bash
npm run typecheck    # tsc --noEmit
npm run lint         # eslint .
npm test             # vitest run
npm run test:watch   # vitest
npm run build        # tsup + explicit template copy
npm run package:check # npm pack --dry-run && publint
```

Release CI should additionally create a real `npm pack` tarball, install it into a fresh fixture repository, run `npx exspecso init` for each selected adapter individually and in combinations, repeat initialization to prove idempotence, and assert that unrelated user files were not changed. Run the resulting CLI on Node 24 and the current Node release.

## Alternatives Considered

| Category | Recommended | Alternative | Why Not |
|---|---|---|---|
| Runtime | Node 24+ ESM | Bun/Deno-first runtime | All required hosts, npm distribution, and native CLI conventions already center Node. Another runtime creates a compatibility boundary without user value. |
| Package structure | One npm package with `src/` boundaries | Monorepo / separate core and adapters packages | The V1 release cadence and artifact model are shared. Multiple packages introduce version-skew and installation complexity before there is a real independent-release need. |
| Canonical storage | Markdown + JSON + Git | SQLite, ORM, cloud database | Violates the explicit artifact-first constraint and makes cross-runtime recovery dependent on hidden state. |
| CLI | Commander | oclif, Ink, custom argument parser | oclif/Ink add framework weight and a UI model V1 does not need; a custom parser adds avoidable edge cases. Commander is enough for an intentionally quiet CLI. |
| Validation | Zod | TypeScript types alone | Static types cannot reject malformed or manually edited files at runtime. |
| Build | tsup ESM CLI bundle | Dual ESM/CJS output | The CLI has no requirement to be imported by legacy CommonJS consumers. Dual output doubles release and test surface. |
| Git wrapper | Native `child_process` argument arrays | `simple-git` or shell snippets | Exspecso needs a narrow deterministic Git surface. Native APIs keep dependencies and shell-injection exposure low. |
| Claude integration | Native templates/plugin assets | Claude Agent SDK as the workflow engine | Exspecso must run as a local harness across three runtimes; adopting any one agent SDK as the core would break adapter neutrality. |
| OpenCode integration | Project command Markdown | V2 plugin API | Official docs label the V2 plugin API beta; command files meet V1 needs with less moving surface. |
| Testing | Vitest + fast-check + tarball fixtures | Only unit tests or broad E2E after every task | Unit tests alone miss filesystem/install contracts; blanket E2E conflicts with proportionate evidence. Combine properties, focused fixtures, and release smoke tests. |

## Avoid in V1

- A web server, daemon, worker queue, WebSocket channel, telemetry dependency, user account, or cloud control plane.
- A runtime-specific agent SDK as the core implementation.
- Runtime plugins that silently mutate canonical files on lifecycle events; all mutation must be attributable to an explicit Exspecso operation.
- A generated “status database,” duplicated artifact index, or cache that users must trust more than repository files.
- General-purpose workflow engines, state-machine frameworks, or event sourcing. The transition graph is small and safety-critical; write it explicitly, test it exhaustively, and derive state from artifacts.
- Interactive TUI frameworks, spinners, or progress renderers that make non-interactive agent invocation fragile. Favor stable text/JSON output modes.
- Shell interpolation for Git or filesystem work, and automatic repair of malformed user artifacts.

## Installation

```bash
# Runtime dependencies
npm install commander@^15.0.0 zod@^4.4.3 yaml@^2.9.0

# Development dependencies
npm install -D typescript@^7.0.2 tsup@^8.5.1 vitest@^4.1.10 \
  fast-check@^4.9.0 tsx@^4.23.12 eslint@^10.8.1 prettier@^3.9.6 publint@^0.3.23
```

Version policy: pin the Node compatibility floor in `engines`, use compatible ranges for application dependencies, and commit the lockfile. Before every release, resolve current dependencies in CI, run the full suite, inspect `npm pack`, and update this research decision only when an adapter or Node LTS transition changes supported behavior.
